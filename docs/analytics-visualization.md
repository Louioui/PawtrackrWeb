# Pawtrackr analytics visualization contract

## Authenticated staff read view

`/dashboard/analytics/live` is a separate source-backed view for a provisioned staff account. Its claim is limited to recorded completed checkout totals; it does not call them settled revenue. The API derives the salon from active staff membership under RLS, returns 7, 30, or 90 UTC daily buckets, and marks `settlement_confirmed: false`. The screen shows the total and period first, then a zero-baseline daily line, with an exact-value table and CSV beside the same data. On a narrow phone, the chart stays above the table. The source, UTC convention, as-of time, and payment caveat remain visible without hover.

The live view retains its last in-memory snapshot during offline or failed refresh and says so in the status badge. It does not persist private analytics data in the demo service-worker cache. A sign-out, expired session, or revoked staff membership clears the snapshot. Browser QA covered the 390 px unauthenticated and failed sign-in states, plus a mocked authenticated chart, exact daily table, CSV export, offline last-known-good state, and revoked-membership state. A temporary real Auth account also signed in and saw only its salon's hosted $12.34 checkout while another fixture salon's $99.99 was excluded; the fixture was removed after verification. Production account provisioning remains to be built.

## Reading and interaction contract

- Desktop: selected business and window above one dominant daily-total chart, period summary beside it, package grouping and recent checkouts below.
- Mobile portrait: title, business/window controls, and primary chart appear before secondary details. Controls use native selects with touch-sized targets. A daily value table and CSV export are available beside the chart. A deterministic Playwright screenshot baseline covers the primary card at 390 px width, including the chart, status, table control, and source note.
- At 320 px, the period summary and full document fit without horizontal page scrolling. The shared header hides its secondary brand badge and displays Station PIN as an accessible icon link at this width, leaving the portal switcher as its own horizontally scrollable row. The narrow-phone browser check protects this layout.
- The global tour and support widget follows page content in document flow, so its control does not cover the mobile chart or daily-value table. The mobile browser test checks that its button sits below the primary chart.
- No hover is required to read the total, time window, zero-based daily scale, source caveat, or exact daily values. The chart has an accessible summary; the expandable table supplies the daily values.
- A mobile-width axe audit now scans the complete analytics page for WCAG 2 A/AA and 2.1 A/AA rule violations. The shared icon-only Quick Jump button was given an accessible name and the tour button's name now contains its visible text. A browser test also opens and closes the daily-values disclosure using Enter and checks its 30 rows. These checks do not replace screen-reader review.
- Changing business or period recomputes chart, summary, package ranking, table, and CSV from the same pure aggregation. Empty windows show an explicit empty state. A single active day is labeled as insufficient for a trend. Completed zero-dollar checkouts retain their count and table rows but show an explanatory state instead of an invented one-cent plot scale.
- Browser-offline, server-unavailable, checking, and delayed states keep the last local snapshot visible. The demo ledger is checked on mount, every 60 seconds while the tab is visible, and after browser reconnect or tab resume. The status describes the connection rather than implying that the data is live or settled.
- Demo edits retain the latest whole snapshot and its pre-edit base in browser storage until `/api/store` acknowledges it. Reconnect triggers a retry. A three-way comparison merges independent business configs and entity IDs; competing edits to one ID stay pending with a conflict badge. This is a local-demo recovery path, not production conflict resolution.
- While an edit awaits acknowledgement, the source badge says that local edits are pending sync and uses the caution color, even when the last server check succeeded. The badge clears after the pending snapshot is acknowledged.
- A server refresh does not replace the visible local snapshot while an edit is pending. On mount and reconnect, the app retries that snapshot before applying a server refresh. A second tab sees the pending badge change through browser storage events.
- After a successful demo write, the browser adopts the server's acknowledged snapshot and revision timestamp only if no newer local edit has replaced the queued snapshot. The disk ledger increments its revision timestamp monotonically. A stale `If-Match` revision rejects the write. This still lacks cross-process atomicity and durable per-record versions.
- The daily CSV includes business ID, UTC date, recorded completed demo checkout cents, whether an edit was pending sync, and the snapshot status at export time (`server_reached`, `checking_server`, `server_unavailable`, `server_delayed`, `browser_offline`, `pending_sync`, or `sync_conflict`). Its filename also identifies the demo, business, and date window. This status describes reachability and conflict state, not payment settlement or the origin of every record.
- Completed checkout total and average checkout are compared with the immediately preceding UTC window of the same length, cut off at the same UTC time on its final day. The summary shows the prior total, total change, prior average, and checkout count. Percentage change is omitted when the prior value is zero; change is omitted when the prior window has no checkouts. This keeps a partial current day from being compared with a full prior final day.
- Settings can save an optional weekly demo checkout target in integer cents per salon. The analytics summary then shows recorded completed checkouts from UTC Monday through today against that target and a linear seven-day pace. The target is owner-entered, not a forecast; pending and refunded records stay excluded. The browser test verifies save → analytics display and that another salon does not inherit the target.
- Current-period totals and weekly pacing stop at the current instant, so a demo checkout timestamp later today does not appear early. Prior-window comparisons still use their full UTC date windows. A unit test and browser fixture cover the future-today case.
- Add-on selection rate divides distinct linked visits with at least one selected add-on by all distinct visits linked to completed checkouts. When there are no linked visits, the rate is undefined rather than zero. Unlinked checkouts remain in the total but do not enter this denominator.
- Switching demo businesses clears the prior business's server-response timestamp until the newly selected business is checked. The status badge announces changes to assistive technology. At 90 days, the chart omits crowded point markers when more than one day has a positive total; the daily values table and CSV retain every date and value.
- The selected demo business and 7, 30, or 90 day window are stored in the analytics page URL. A shared URL restores both controls after hydration; unknown business IDs and unsupported windows fall back to the default selection.

## Implementation and performance

One SVG plot with at most 90 daily points is visible at once. The package ranking uses HTML bars. At 90 days, the chart uses about 90 plotted points plus three grid lines, well below a dense-mark renderer threshold. Aggregation scans transactions and visits once per selected business/window change; the page refreshes the status clock once a minute. A single in-flight demo ledger request is allowed per subscription, with a 60-second visible-tab refresh cadence for analytics. SVG and semantic HTML are preferred here for maintainability, accessible labels, and static screenshot/export fidelity. Canvas or WebGL would add complexity without a demonstrated mark-count or frame-budget need. If the ledger grows materially, move date-window aggregation to a tenant-scoped server query and return bounded daily rollups rather than rendering raw transactions.

## QA boundary

`npm test` checks cent precision, UTC boundaries, tenant filtering, pending/refunded exclusion, duplicate IDs, missing visit links, sparse and empty periods, CSV rows, and source-status labels. `npm run typecheck` and `npm run build` cover the app integration. Browser review has covered mobile portrait, desktop geometry, business/window changes, empty state, the daily table, CSV download, and the offline → checking → server-reached reconnect transition while retaining the chart. Before production release, add authenticated tenant-scoped data access, payment-settlement confirmation, refund ledger semantics, and itemized checkout lines. Then test stale/reconnect behavior and payment-state transitions against that real backend.

`npm run test:e2e` builds and serves the production bundle on port 3011, then runs Playwright checks in installed Chrome. Analytics checks seed local illustrative records in fresh browser contexts and verify filter restoration, seven daily rows, the labeled cent-based CSV sum, mobile chart-before-summary order at 390 × 844, an explicit empty salon state, and a prior-period total cut off at the same UTC time. A mocked `/api/store` response plus browser offline emulation verifies that the chart remains visible while its source badge moves from server reached to offline and back. The production API remains disabled; the reconnect test mocks it at the browser network boundary. Playwright blocks the app's service worker for these checks so the route mock receives requests reliably. They cover browser integration and basic geometry; they are not tests of authenticated production data. Client weight checks are described in `docs/client-weight-visualization.md`.

Two separate Playwright checks allow the service worker. One verifies that, immediately after worker activation, the first offline reload hydrates and the 90-day control renders 90 table rows with Chrome's ordinary HTTP cache disabled. The other verifies that `/api/store` and `/client/[id]` responses never enter Cache Storage. During install, the worker caches listed demo app-shell pages and their referenced same-origin Next.js static assets. API requests pass through to the network so the dashboard status reflects a failed fetch. This is a demo cache boundary. Authenticated or personalized HTML must be removed from the shell list before introducing production login.

The service-worker cache test accepts HTTP 503 from the disabled production demo API or HTTP 429 when the shared in-process IP limiter has already handled many suite requests. Both are live network rejections; the assertion that no `/api/` response enters Cache Storage remains unchanged. A 10-run repeat and the complete 20-test browser suite passed after this correction.

A production-build browser check at 390 × 844 confirmed that selecting 90 days updates the chart date range and prior-period label. The 90-day single-observation view remains readable, and the disabled production demo API yields a server-unavailable badge while retaining the local illustrative snapshot. An earlier development-server check was invalid because its layout chunk failed to load; the production build was checked separately after clearing the generated `.next` output.

A fresh development-server check reproduced an initial `app/layout.js` syntax error in the browser, with the 90-day selector changing without chart hydration. Reloading that page restored hydration: the selector then updated the chart. The exact cause of the first-load development chunk error remains unverified. The production build and its browser interaction were unaffected in the separate check.

The local demo store now checks the basic record shapes required by the visualizations before accepting a server write or cached snapshot. This prevents malformed demo transactions from crashing the analytics transform; it is not a production data schema or authorization layer. A runtime check accepted the current transaction snapshot (HTTP 200), rejected malformed transaction data (HTTP 400), and confirmed the transaction list was unchanged after the rejection.

Offline retry was exercised in a separate ledger on port 3001 using `PAWTRACKR_DEMO_DATA_DIR=/tmp/pawtrackr-sync-qa`: one pending transaction appeared in browser storage while offline, the server stayed at one transaction, then reconnect cleared the pending snapshot and brought the server to two transactions. The added transaction remained `pending`, so it did not enter completed checkout totals. This proves the single-browser demo retry path, not concurrent-device conflict handling.

Revision acknowledgement was exercised in another isolated ledger on port 3005. After a pending van checkout preview, browser and server both held 2 transactions and revision `1794236905577`, with no pending snapshot. After a no-show fee preview, both held 3 transactions and revision `1794236927775`, again with no pending snapshot. This verifies the ordinary sequential demo write path; it does not prove safety for simultaneous edits from multiple devices.

Conflict QA used an isolated development ledger and two fresh browser contexts. The first saved a $70 weekly target and cleared its pending snapshot; the second, which had loaded before that write, saved an $80 target and retained it locally with a conflict flag. The server kept $70. A production-build browser test mocks this sequence and verifies the Settings alert and analytics conflict badge. Direct development API checks returned 428 without `If-Match`, 409 for a stale revision, 200 for the current revision, and 409 when reusing that old revision. The test does not establish safety for writes from multiple server processes.

The two-browser test also covers independent salon settings: after one browser saves a $70 target for Bespoke, a browser holding an older snapshot saves an $80 target for Splash. The rebuilt production client merges the settings by business ID, clears the pending edit, and the shared demo ledger retains both targets. The record merge unit tests cover independent entity IDs, competing changes to one ID, and duplicate-ID rejection.

The demo store validator rejects duplicate IDs within each entity array, including transactions, before a whole-snapshot write. This prevents an ambiguous checkout record from entering the ledger through `/api/store`; the duplicate-ID unit cases cover transactions and clients. Existing historical or external data still needs source-level validation in a production pipeline.
