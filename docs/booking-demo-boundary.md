# Public booking demo boundary

The public booking page is a local demo. A successful development-mode submission now receives server-created client, pet, and visit records and adds those same records to the browser's demo store. A two-pet request creates two pet records and two visits under one client. The server validates that the salon, package, add-ons, and selected staff belong together and calculates the quoted amount from the salon catalog in integer cents; caller-supplied totals are ignored. It rejects malformed or past dates, unknown catalog IDs, and staff from another salon.

The form shows a confirmation only after the server returns those records. Network errors and non-2xx responses display an error without inventing a booking or changing the browser store. In production, `/api/bookings` remains disabled with HTTP 503 until authenticated booking, availability, anti-abuse controls, and a real database are implemented. The browser test in `tests/e2e/booking-boundary.spec.ts` verifies that production failure does not create a false confirmation.

Local QA with an isolated development ledger submitted a two-pet Splash booking: a cross-salon staff ID returned 400; a valid request returned 200 with two pets, two matching visits, and a server-calculated $267.25 total despite a submitted `$1` total. The ledger gained one client, two pets, and two visits. This is a demo integrity check, not a production booking acceptance test.

The settings page now saves a validated demo catalog into the local store. The public booking page and command-center POS preview read that same saved catalog, including cross-tab demo updates; selecting a package updates the displayed quote. The browser test in `tests/e2e/catalog-preview.spec.ts` verifies that a new package appears in the right salon's booking page and POS preview, changes its quote, and stays absent from the other salon. A local save is not a production database write or proof of server acknowledgement.

A separate development-mode check used an isolated ledger and two fresh browser contexts. Saving a package in Settings wrote it to `/api/store` under the selected salon's `custom_settings.packages`; the booking page in the second context displayed it. This confirms the demo server sync path in development. The production build still disables `/api/store`, so this check does not establish a production catalog workflow.

Slots are still sample preferences, not live availability. The page does not perform photo analysis, send SMS, save a payment method, place a cancellation hold, create a membership, or award loyalty points. Before release, add request-scoped tenant authorization for staff actions, public booking rate limits and bot defenses, salon timezone and capacity rules, duplicate booking prevention, consent and contact verification, and a durable transactional database write. The production form and server must query the salon's current authorized catalog rather than trusting a browser snapshot.
