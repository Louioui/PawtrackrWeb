# Production data boundary

Pawtrackr currently runs with an unauthenticated disk-backed demo ledger. Its local demo endpoints are intentionally disabled when `NODE_ENV=production`:

- `GET` and `POST /api/store`
- `POST /api/checkout`
- `POST /api/bookings`
- `POST /api/billing/subscribe`

Each returns HTTP 503 and `Cache-Control: no-store`. Public pages still contain only the checked-in illustrative data. The middleware identifies this as `x-pawtrackr-data-mode: demo-only`; it no longer claims that the disk ledger is RLS protected.

The separate `GET` and `POST /api/analytics` endpoints use a project publishable key and a caller bearer token. `GET` verifies the token with Supabase Auth, requires an active staff membership, and reads completed transactions and eligible un-checked-out visits through caller RLS. `POST` validates integer-cent checkout amounts (`subtotal - discount + tax + tip`), rejects duplicate completed checkouts for the same visit with HTTP 409, inserts the completed transaction under caller RLS, and marks the visit completed. Totals distinguish recorded checkouts from confirmed settlement. `/dashboard/analytics/live` consumes both endpoints after email/password sign-in; the original dashboard analytics page remains labeled demo data. Built-server requests without a token or with an invalid token returned 401, and invalid cent math returned 400. A temporary real Auth user assigned to salon A saw its $12.34 checkout and did not see salon B's $99.99 checkout. Deactivating that staff membership cleared the chart on refresh. The QA user and all fixture rows were removed afterward. Self-serve provisioning is implemented through the invoker/private RPC boundary, but still needs a real hosted Auth provisioning run.

`POST /api/reservations` and `PATCH /api/reservations` are separate staff-only write paths. `POST` verifies the bearer token through Supabase Auth, checks active staff membership, validates an offset-aware future time and tenant-scoped pet/groomer, derives duration, price, and buffer from the salon catalog, checks configured local hours in the salon's IANA time zone, and writes using the caller token under RLS. `PATCH` updates an existing visit's status inside the caller's active salon under RLS. PostgreSQL exclusion errors return 409 on both endpoints. The production build and browser rejection checks for missing or invalid credentials passed, and a real Auth-backed hosted write returned 201, then 409 for an overlap and 201 for an adjacent slot before the local-hours change. A later real Auth-backed shift fixture returned 422 outside a scheduled shift and 201 inside it. Both QA fixtures were deleted; hosted follow-up counts were zero. The staff calendar now uses salon-local day bounds, while public customers book through the separately restricted anonymous RPC path.

`GET /api/reservations?date=YYYY-MM-DD` now provides a staff-only UTC daily read, limited to 1,000 visits, along with the tenant's active booking options (pets, groomers, and configured services). It verifies the caller’s Auth session and active staff membership, queries under caller RLS, and returns appointment times, statuses, and tenant-scoped pet, client, and groomer labels with a source and as-of timestamp. `/dashboard/appointments/live` consumes `GET`, `POST`, and `PATCH /api/reservations` across desktop, mobile portrait, and mobile landscape layouts. Built-server rejection tests passed for missing or invalid sessions and malformed dates, and mocked browser E2E and axe checks passed for the staff UI (including new bookings, status updates, and 409 overlap handling). A temporary real Auth staff session read one hosted salon A appointment with its pet, client, groomer, and buffered end time; salon B’s appointment was excluded. The 390 px agenda displayed only salon A’s pet. Deactivating the membership returned HTTP 403. Both fixture salons and the QA user were deleted; hosted follow-up counts for businesses, staff, clients, pets, visits, and Auth users were zero. The staff calendar CSV contains only the currently visible groomer-filtered visits and labels UTC, source, as-of time, and snapshot freshness; untrusted name and service text is escaped for spreadsheet import.

Staff settings store an IANA time zone in `custom_settings.time_zone`. Staff creation requires valid configured hours and reserves enough time for the service plus its booking buffer before closing in that local zone, including daylight-saving transitions. Existing settings without a zone use UTC until the salon configures one. The GET response withholds bookable services if hours or zone are malformed. For non-UTC salons, the staff appointment form converts a selected local date and time to a unique UTC instant, rejecting skipped and repeated clock minutes. Reservation reads resolve a salon-local day to exact UTC bounds, and calendar labels and navigation render in that salon zone.

The staff reservation API reads `staff_shifts` under the caller's RLS for the groomer and salon-local date. When rows exist, `time_off` blocks booking and a `scheduled` window must contain the full service and buffer. Empty shift days retain operating-hours-only behavior. `/api/shifts` verifies a staff bearer token and active membership for dated reads, groomer shift writes, and deletion; local shift clocks are validated against the salon's IANA zone, rejecting skipped or repeated DST minutes. The live settings page includes a local-date add/remove shift editor. A temporary real Auth staff session created and read a hosted scheduled shift, received 422 outside the shift and 201 inside it, deleted the shift, and then received 403 after staff membership deactivation. A later real anonymous booking ran through the same hosted visit trigger, removed every overlapping service-plus-buffer start from availability, and caused a second attempt at the occupied start to fail with `PW022`. Both fixtures were deleted; Auth and production-table counts returned to zero.

Migration `0015_publish_salon_time_zone.sql` adds `time_zone` to the restricted public booking catalog and its service view. The refresh trigger copies `custom_settings.time_zone` or UTC for legacy settings; the live catalog displays it beside published hours. Local PostgreSQL verified trigger projection; hosted catalog inspection confirmed the new column, view definition, and `security_invoker=true`. A temporary hosted salon exposed `America/Los_Angeles` via the anonymous publishable-key Data API, and the built live page rendered `08:00–18:00 America/Los_Angeles`. The fixture was deleted; follow-up counts for businesses, configs, and public catalog were zero.

The separate `/portal/live` directory and `/portal/live/[slug]` detail pages read only the public booking directory and service catalog views with a publishable key. A temporary active salon appeared with its published services, and changing its subscription to canceled hid both the listing and detail page. The live detail page includes transactional availability and booking submission through restricted anonymous-safe RPC wrappers. A hosted anonymous Data API fixture returned valid salon-local starts, booked one, withheld its overlapping window, and rejected a duplicate start without returning a groomer or internal IDs. Demo salon pages are noindexed and excluded from the dynamic sitemap.

This is a release gate, not a production backend. The dedicated Pawtrackr Supabase project has the schema installed. To replace the gate, verify its RLS with real Auth and Storage flows, implement real staff and client authentication, and authorize every API request from a verified user identity and tenant membership. A caller-supplied `business_id` or a front-end tenant switch cannot authorize a request. The route must use a request-scoped user context, and database queries must respect RLS. Payment completion must be confirmed by a verified Stripe event before checkout totals are described as settled revenue. Stripe webhooks must reject missing or invalid signatures.

The optional browser Supabase client no longer sends a caller-selected `x-pawtrackr-business-id` header. That header never established authorization and could remain stuck on the first selected salon because the client is a singleton. The optional broadcast subscription only asks the local demo store to refresh; it is not a production data channel. A production client must use authenticated, private subscriptions and RLS-backed queries tied to active staff membership.

In local development, the legacy checkout and demo-booking endpoints write only to the demo ledger, even if Stripe or Supabase environment variables are present. Subscription signup remains a preview without creating a Stripe Checkout session or tenant. The separate production Stripe webhook returns 503 when its webhook secret or Supabase service credential is absent and rejects unsigned or forged events before any database call. Live settlement still requires a real Stripe test-mode and deployment run.

The demo booking endpoint rejects a requested groomer slot when it overlaps an existing active visit for that business and staff member. It uses the selected package durations, including both pets in a multi-pet booking, and returns HTTP 409 before creating records. The second pet's visit starts after the first pet's service so later availability checks see the full occupied interval. A local isolated-ledger check returned 200 for the first booking and 409 for the same request; the ledger retained one new visit. A separate multi-pet check recorded starts at 09:00 and 11:00, then rejected a 12:00 overlapping request. This remains a wall-clock demo check. Separately, the hosted database's atomic exclusion constraint, salon-zone hours, buffer, and anonymous booking path now have real Data API fixture evidence.

The public demo portal uses the latest local schedule to disable overlapping sample slots and explains when a selected time becomes occupied. A browser check at a fixed date verifies that a 10:30 slot is disabled for the busy groomer, 12:00 remains selectable, and the same 10:30 slot is available for a different groomer. The local schedule can be stale; the API overlap check remains the final demo gate.

The command center POS now treats API errors as failures instead of fabricating a completed transaction. Its successful state is labeled as a demo record with no payment charged. Van checkout and no-show fee scenario triggers create pending demo records, which are excluded from the completed checkout analytics and drawer summary. SMS, waitlist, and QR payment interactions are labeled as previews because no provider delivery or payment link exists.

The POS client accepts only a successful demo response with the expected business, visit, amount, and completed status. Disk ledger writes use a temporary file and rename; write failures now propagate to the API instead of returning an apparent success. This is still a single-machine demo ledger and does not provide multi-device transaction isolation.

The demo checkout API now rejects a second completed checkout for the same salon visit with HTTP 409 and uses a random UUID for each new transaction. An isolated development-ledger check returned 200 then 409 for the same checkout request; the ledger contained one completed transaction for that visit. This prevents ordinary repeat submissions from inflating demo analytics in one process. Real payments need an idempotency key and an atomic database/payment-provider flow across processes.

For isolated local QA, `PAWTRACKR_DEMO_DATA_DIR` can point the disk ledger at a temporary directory. Browser edits queue the latest complete demo snapshot with its pre-edit base in local storage and retry on reconnect. The browser compares configs by business ID and entity records by ID against the current server snapshot. Identical changes or edits to different IDs merge; competing edits to one ID stay local with a visible conflict alert. The server also requires `If-Match` with the current ledger revision (428 if missing, 409 if stale) before a whole-snapshot write. This is a single-process demo safeguard, not transactional multi-device conflict resolution. Production needs durable per-record versions and conflict handling.

Development-only `GET /api/store?business_id=...` now filters `configs` as well as clients, pets, visits, and transactions to the requested salon. An empty query value returns 400; an unknown value returns empty collections. An isolated local-ledger check exercised both known salons and the empty/unknown cases. This is response shaping only: the unscoped demo route still exposes the full illustrative ledger, and a caller-supplied ID is not authentication.

Verification performed on the configured production build: protected routes reject missing sessions with 401, malformed inputs with 400/422 as appropriate, and forged Stripe signatures with 400. A deliberately configuration-free run returned 503 for live routes, confirming the fail-closed boundary. `npm test`, `npm run typecheck`, `npm run build`, and all 44 Playwright scenarios pass. The Pawtrackr Supabase schema is installed through migration 0022; staff reads/writes have real Auth-backed hosted evidence and public booking has real anonymous Data API evidence. Owner provisioning, Stripe, and Storage retain the explicit gaps listed below.

`npm run migrate:check` is a static inventory gate: it checks sequential filenames, nonempty files, and prints SHA-256 prefixes. `npm run test:migrations` creates a temporary local PostgreSQL database, applies all twenty-two migrations, and checks selected client tenant filtering, cross-business reference rejection, privileged RPC grants, grooming photo visibility, public booking views and published time zone, active staff identity binding, database availability rules, public booking, settlement transitions, and the private implementation/public invoker RPC boundary using a minimal Supabase auth/storage fixture. PostgreSQL 14 is used locally and the hosted project currently runs PostgreSQL 17.11. Hosted role-simulation checks also passed and rolled back their fixtures. These tests do not verify a real Supabase Auth token, Storage request, every table policy, or production tenant authorization end to end.

Local testing found that an authenticated tenant could call the `SECURITY DEFINER` payroll function with another tenant's `business_id` and receive its staff ledger. Migration `0004_restrict_privileged_rpcs.sql` removes direct `anon` and `authenticated` execution grants from payroll and checkout RPCs and grants execution to `service_role`. A future server implementation must verify the caller's identity and tenant membership before using that role; possession of the service key alone is not tenant authorization. Supabase's native migration history records the hosted migrations; the app no longer creates a parallel history table with placeholder checksums.

Migration `0005_enforce_tenant_references.sql` rejects existing cross-business references during upgrade and adds triggers to enforce same-business links between clients, pets, visits, transactions, waivers, credits, shifts, and reviews on future writes. Migration `0006_private_grooming_photos.sql` changes the grooming photo bucket to private, removes anonymous object reads, and scopes staff reads and mutations to their business folder. Client photo access will need an authorized server endpoint that issues short-lived signed URLs; the current demo portal does not provide that production flow.

Migration `0007_public_booking_views.sql` removes direct public reads of full business and configuration rows. It exposes only active salon directory fields and booking catalog fields through dedicated views. Staff still see their own full rows through RLS. The implemented public directory and booking flow use these restricted projections and the anonymous-safe RPC wrappers rather than the underlying tables.

Migration `0008_bind_tenant_to_active_staff.sql` makes `current_business_id()` resolve a tenant only from an active `staff_members` row matching `auth.uid()`. If a JWT tenant claim exists, it must match that row. A claim alone, a missing user ID, or an inactive staff row yields no tenant access. Provisioning must create the staff membership through a trusted server path before staff use the dashboard.

Migration `0012_atomic_staff_reservations.sql` computes a visit’s end from its duration and buffer on every insert or update. A GiST exclusion constraint rejects overlaps for the same business and assigned groomer while the visit has an active status. `0013_move_btree_gist_extension.sql` moves the supporting extension out of `public`. `0014_harden_transaction_checkout_invariants.sql` enforces `discount <= subtotal AND amount = subtotal - discount + tax + tip` and a partial unique index `transactions_one_completed_per_visit` on `public.transactions` so concurrent requests cannot record two completed checkouts for the same visit. Migration 0014 is installed on the dedicated hosted project; direct catalog inspection found both constraint definitions and the hosted security advisor returned no findings. Local PostgreSQL tests exercised the rejection behavior; the hosted database was inspected but not seeded for another write test. `/api/clients` (`GET`, `POST`, and `PATCH`) and `/dashboard/clients/live` allow signed-in staff to view and register tenant clients and pets and update pet weight observations under caller RLS. `/api/settings` (`GET`, `PATCH`, and `POST`) and `/dashboard/settings/live` allow signed-in staff to read and update salon operating hours, turnaround buffers, tax rates, service packages, spa add-ons, and groomer staff under caller RLS, automatically refreshing the public booking catalog table.

## Sign-up, public booking, and settlement

`POST /api/webhooks/stripe` is no longer a disabled demo route. It returns 503 until `STRIPE_WEBHOOK_SECRET` and `SUPABASE_SERVICE_ROLE_KEY` are set, 400 unless Stripe's signature verifies over the raw request body, and otherwise passes the event to `public.apply_stripe_payment_event`. This is the only route that uses the service-role key, and it does so only after verification.

`GET` and `POST /api/onboarding` verify a bearer token with Supabase Auth. `POST` calls `public.provision_salon` with the caller's own token; the function derives the owner from `auth.uid()`.

`GET /api/public/availability` and `POST /api/public/bookings` use the publishable key with no user session and call only `public_booking_slots` and `public_book_appointment`. The salon is identified by its public slug; price, duration, buffer, and groomer are decided in the database. Neither response includes another client's data, an internal id, or a groomer.

`POST /api/payments/intent` verifies a staff bearer token, reads the transaction under caller RLS, and takes the charge amount from the stored row. It uses the transaction id as Stripe's idempotency key and cancels the intent if it cannot be linked to the checkout.

Migrations `0016`–`0022` are installed on the dedicated hosted project and verified in temporary PostgreSQL. Hosted inspection confirmed the availability trigger, settlement columns, intended grants, private privileged implementations, public invoker wrappers, explicit no-client-access webhook ledger policies, covering foreign-key indexes, and removal of a duplicate schedule index. A real anonymous Data API fixture verified slot discovery, booking, occupied-window removal, and duplicate rejection; cleanup returned all production-table and Auth counts to zero. Supabase security and health advisors report no findings; the remaining performance notices are unused-index information expected for an empty database, not missing-index or duplicate-index warnings. Real hosted Auth provisioning, real Stripe events, and real Storage delivery remain unverified; see [build status](build-status.md).

## Dependency audit

The November 9, 2026 package audit found that Next.js 15.5.29 pinned a nested PostCSS 8.4.31, which was within the affected range of the [source-map file disclosure advisory](https://github.com/advisories/GHSA-r28c-9q8g-f849) and its [incomplete-fix follow-up](https://github.com/advisories/GHSA-fxqj-rqcc-2cmp). The root PostCSS dependency was already 8.5.32. `package.json` now pins the direct dependency and overrides the nested copy to 8.5.32. `npm ls next postcss` shows every installed PostCSS copy at 8.5.32. A fresh November 10 `npm audit --json` reports zero findings across 169 dependency entries, and CI now rejects high or critical advisories. `npm outdated` lists major migration tracks rather than compatible patch updates; Next 16, Stripe 23, Tailwind 4, Lucide 1, TypeScript 7, and Node 26 types were intentionally not introduced during this hardening pass. The current 72 Node tests, TypeScript typecheck, production build, and 44 Playwright scenarios pass with the existing supported stack. This validates the tested flows; it does not establish compatibility for untested Next.js internals or replace planned framework upgrades.
