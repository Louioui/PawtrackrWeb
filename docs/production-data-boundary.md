# Production data boundary

Pawtrackr currently runs with an unauthenticated disk-backed demo ledger. Its local demo endpoints are intentionally disabled when `NODE_ENV=production`:

- `GET` and `POST /api/store`
- `POST /api/checkout`
- `POST /api/bookings`
- `POST /api/billing/subscribe`
- `POST /api/webhooks/stripe`

Each returns HTTP 503 and `Cache-Control: no-store`. Public pages still contain only the checked-in illustrative data. The middleware identifies this as `x-pawtrackr-data-mode: demo-only`; it no longer claims that the disk ledger is RLS protected.

The separate `GET` and `POST /api/analytics` endpoints use a project publishable key and a caller bearer token. `GET` verifies the token with Supabase Auth, requires an active staff membership, and reads completed transactions and eligible un-checked-out visits through caller RLS. `POST` validates integer-cent checkout amounts (`subtotal - discount + tax + tip`), rejects duplicate completed checkouts for the same visit with HTTP 409, inserts the completed transaction under caller RLS, and marks the visit completed. Totals describe recorded checkouts, not payment settlement. `/dashboard/analytics/live` consumes both endpoints after email/password sign-in; the original dashboard analytics page remains labeled demo data. Built-server requests without a token or with an invalid token returned 401, and invalid cent math returned 400. A temporary real Auth user assigned to salon A saw its $12.34 checkout and did not see salon B's $99.99 checkout. Deactivating that staff membership cleared the chart on refresh. The QA user and all fixture rows were removed afterward; production provisioning is still absent.

`POST /api/reservations` and `PATCH /api/reservations` are separate staff-only write paths. `POST` verifies the bearer token through Supabase Auth, checks active staff membership, validates an offset-aware future time and tenant-scoped pet/groomer, derives duration, price, and buffer from the salon catalog, and writes using the caller token under RLS. `PATCH` updates an existing visit's status inside the caller's active salon under RLS. PostgreSQL exclusion errors return 409 on both endpoints. The production build and browser rejection checks for missing or invalid credentials passed, and a real Auth-backed hosted write returned 201, then 409 for an overlap and 201 for an adjacent slot. The temporary salon, visits, and QA account were deleted; hosted follow-up counts were zero. This path does not enforce salon hours, staff shifts, or local time-zone rules and is not exposed as public online booking.

`GET /api/reservations?date=YYYY-MM-DD` now provides a staff-only UTC daily read, limited to 1,000 visits, along with the tenant's active booking options (pets, groomers, and configured services). It verifies the caller’s Auth session and active staff membership, queries under caller RLS, and returns appointment times, statuses, and tenant-scoped pet, client, and groomer labels with a source and as-of timestamp. `/dashboard/appointments/live` consumes `GET`, `POST`, and `PATCH /api/reservations` across desktop, mobile portrait, and mobile landscape layouts. Built-server rejection tests passed for missing or invalid sessions and malformed dates, and mocked browser E2E and axe checks passed for the staff UI (including new bookings, status updates, and 409 overlap handling). A nonempty real Auth-backed hosted read is not yet verified.

The separate `/portal/live` directory and `/portal/live/[slug]` detail pages read only the public booking directory and service catalog views with a publishable key. A temporary active salon appeared with its published services, and changing its subscription to canceled hid both the listing and detail page. The fixture was deleted. The live detail page has no booking submit action because transactional availability and public reservation authorization are not ready. Demo salon pages are noindexed and excluded from the dynamic sitemap.

This is a release gate, not a production backend. The dedicated Pawtrackr Supabase project has the schema installed. To replace the gate, verify its RLS with real Auth and Storage flows, implement real staff and client authentication, and authorize every API request from a verified user identity and tenant membership. A caller-supplied `business_id` or a front-end tenant switch cannot authorize a request. The route must use a request-scoped user context, and database queries must respect RLS. Payment completion must be confirmed by a verified Stripe event before checkout totals are described as settled revenue. Stripe webhooks must reject missing or invalid signatures.

The optional browser Supabase client no longer sends a caller-selected `x-pawtrackr-business-id` header. That header never established authorization and could remain stuck on the first selected salon because the client is a singleton. The optional broadcast subscription only asks the local demo store to refresh; it is not a production data channel. A production client must use authenticated, private subscriptions and RLS-backed queries tied to active staff membership.

In local development, checkout and booking endpoints now write only to the demo ledger, even if Stripe or Supabase environment variables are present. Subscription signup returns a preview without creating a Stripe Checkout session or tenant. The webhook endpoint returns 503 in all environments; no unsigned event can update a subscription. These routes remain unsuitable for production until the authenticated payment and data flows are implemented.

The demo booking endpoint rejects a requested groomer slot when it overlaps an existing active visit for that business and staff member. It uses the selected package durations, including both pets in a multi-pet booking, and returns HTTP 409 before creating records. The second pet's visit starts after the first pet's service so later availability checks see the full occupied interval. A local isolated-ledger check returned 200 for the first booking and 409 for the same request; the ledger retained one new visit. A separate multi-pet check recorded starts at 09:00 and 11:00, then rejected a 12:00 overlapping request. This is a wall-clock demo check. The hosted database now has an atomic exclusion constraint for active assigned-groomer reservations, including buffers. The separate authenticated staff reservation API has been tested; salon time zones, staff schedules, and a public booking flow are still needed.

The public demo portal uses the latest local schedule to disable overlapping sample slots and explains when a selected time becomes occupied. A browser check at a fixed date verifies that a 10:30 slot is disabled for the busy groomer, 12:00 remains selectable, and the same 10:30 slot is available for a different groomer. The local schedule can be stale; the API overlap check remains the final demo gate.

The command center POS now treats API errors as failures instead of fabricating a completed transaction. Its successful state is labeled as a demo record with no payment charged. Van checkout and no-show fee scenario triggers create pending demo records, which are excluded from the completed checkout analytics and drawer summary. SMS, waitlist, and QR payment interactions are labeled as previews because no provider delivery or payment link exists.

The POS client accepts only a successful demo response with the expected business, visit, amount, and completed status. Disk ledger writes use a temporary file and rename; write failures now propagate to the API instead of returning an apparent success. This is still a single-machine demo ledger and does not provide multi-device transaction isolation.

The demo checkout API now rejects a second completed checkout for the same salon visit with HTTP 409 and uses a random UUID for each new transaction. An isolated development-ledger check returned 200 then 409 for the same checkout request; the ledger contained one completed transaction for that visit. This prevents ordinary repeat submissions from inflating demo analytics in one process. Real payments need an idempotency key and an atomic database/payment-provider flow across processes.

For isolated local QA, `PAWTRACKR_DEMO_DATA_DIR` can point the disk ledger at a temporary directory. Browser edits queue the latest complete demo snapshot with its pre-edit base in local storage and retry on reconnect. The browser compares configs by business ID and entity records by ID against the current server snapshot. Identical changes or edits to different IDs merge; competing edits to one ID stay local with a visible conflict alert. The server also requires `If-Match` with the current ledger revision (428 if missing, 409 if stale) before a whole-snapshot write. This is a single-process demo safeguard, not transactional multi-device conflict resolution. Production needs durable per-record versions and conflict handling.

Development-only `GET /api/store?business_id=...` now filters `configs` as well as clients, pets, visits, and transactions to the requested salon. An empty query value returns 400; an unknown value returns empty collections. An isolated local-ledger check exercised both known salons and the empty/unknown cases. This is response shaping only: the unscoped demo route still exposes the full illustrative ledger, and a caller-supplied ID is not authentication.

Verification performed on the built Next.js server: all five protected route groups returned 503. `npm test`, `npm run typecheck`, and `npm run build` passed in the recent focused runs. The Pawtrackr Supabase schema is installed but the app has not been connected to it for production requests.

`npm run migrate:check` is a static inventory gate: it checks sequential filenames, nonempty files, and prints SHA-256 prefixes. `npm run test:migrations` creates a temporary local PostgreSQL database, applies all thirteen migrations, and checks selected client tenant filtering, cross-business reference rejection, privileged RPC grants, grooming photo visibility, public booking views, and active staff identity binding using a minimal Supabase auth/storage fixture. PostgreSQL 14 was used locally, while the migration target declares Supabase PostgreSQL 15+. Hosted role-simulation checks also passed and rolled back their fixtures. These tests do not verify a real Supabase Auth token, Storage request, every table policy, or production tenant authorization end to end.

Local testing found that an authenticated tenant could call the `SECURITY DEFINER` payroll function with another tenant's `business_id` and receive its staff ledger. Migration `0004_restrict_privileged_rpcs.sql` removes direct `anon` and `authenticated` execution grants from payroll and checkout RPCs and grants execution to `service_role`. A future server implementation must verify the caller's identity and tenant membership before using that role; possession of the service key alone is not tenant authorization. Supabase's native migration history records the hosted migrations; the app no longer creates a parallel history table with placeholder checksums.

Migration `0005_enforce_tenant_references.sql` rejects existing cross-business references during upgrade and adds triggers to enforce same-business links between clients, pets, visits, transactions, waivers, credits, shifts, and reviews on future writes. Migration `0006_private_grooming_photos.sql` changes the grooming photo bucket to private, removes anonymous object reads, and scopes staff reads and mutations to their business folder. Client photo access will need an authorized server endpoint that issues short-lived signed URLs; the current demo portal does not provide that production flow.

Migration `0007_public_booking_views.sql` removes direct public reads of full business and configuration rows. It exposes only active salon directory fields and booking catalog fields through dedicated views. Staff still see their own full rows through RLS. A future public booking flow should query the views, not the underlying tables.

Migration `0008_bind_tenant_to_active_staff.sql` makes `current_business_id()` resolve a tenant only from an active `staff_members` row matching `auth.uid()`. If a JWT tenant claim exists, it must match that row. A claim alone, a missing user ID, or an inactive staff row yields no tenant access. Provisioning must create the staff membership through a trusted server path before staff use the dashboard.

Migration `0012_atomic_staff_reservations.sql` computes a visit’s end from its duration and buffer on every insert or update. A GiST exclusion constraint rejects overlaps for the same business and assigned groomer while the visit has an active status. `0013_move_btree_gist_extension.sql` moves the supporting extension out of `public`; the hosted security advisor reports no findings. Local authenticated-role checks and a rolled-back hosted fixture exercised the constraint. This does not check salon opening hours, groomer shifts, unassigned visits, or public booking authorization.

## Dependency audit

The November 9, 2026 package audit found that Next.js 15.5.29 pinned a nested PostCSS 8.4.31, which was within the affected range of the [source-map file disclosure advisory](https://github.com/advisories/GHSA-r28c-9q8g-f849) and its [incomplete-fix follow-up](https://github.com/advisories/GHSA-fxqj-rqcc-2cmp). The root PostCSS dependency was already 8.5.32. `package.json` now pins the direct dependency and overrides the nested copy to 8.5.32. `npm ls next postcss` shows every installed PostCSS copy at 8.5.32, and `npm audit --json` reports zero findings. The 19 Node tests, TypeScript typecheck, production build, and two Playwright analytics tests pass with that override. This validates the current tested flows; it does not establish compatibility for untested Next.js internals or replace a future framework upgrade.
